You are a classification-design and annotation expert for SWE-bench / agentic coding task data.

Please make the decision directly based on the information provided, and output the final JSON.

The input is a batch of coding task samples. Each sample may contain a user message, an issue description, a requirement statement, a change goal, code context, test information, a patch, a gold diff, run results, or an agent trace.

Your task is to annotate these samples with the dimension `requirement_depth`. This is a **multi-label** dimension; there is no need to inductively derive open-ended categories, as the label set is already fixed. A single task may cover multiple levels at once (for example, both adding a capability and correcting an old behavior), in which case multiple labels should be output.

Dimension definition:
`requirement_depth` describes the level of this task in terms of "requirement abstraction + task type". It answers: how specific were the user's requirements, and is this task more like fixing an explicit bug, adjusting behavior, adding a feature, refactoring/migration, or a version-evolution / roadmap-level requirement?

This dimension focuses on:
- Whether the task goal is a bug, behavior adjustment, feature addition, refactor/migration, or version evolution.
- Whether the requirement is expressed very concretely, or must be inferred from existing behavior, tests, or version information.
- Whether the goal is single and narrow, or a version-level task with multiple goals and multiple constraints.

Do not treat the following as `requirement_depth`:
- Do not look at the interaction pattern, for example whether there are multiple rounds of clarification or retries after failure.
- Do not look at how many files were changed or the size of the patch.
- Do not look at the intensity of tool usage.
- Do not treat implementation means such as "writing tests", "changing configuration", or "changing documentation" as the level itself.

Fixed label definitions:
- `explicit_bug`: An explicit bug. The problem statement directly points out a function, an error phenomenon, an error message, or a very narrow fix target.
- `behavior_adjustment`: Behavior adjustment. The problem statement asks a certain behavior to support some kind of edge case or to correct semantics, but does not directly give a file name.
- `feature_addition`: Feature addition. The problem statement asks for adding some capability, while usually also requiring old behavior or a compatibility path to be preserved.
- `refactor_or_migration`: Refactor or migration. The problem statement asks to replace an internal mechanism, migrate an implementation, or tidy up structure, while keeping external behavior unchanged.
- `release_or_roadmap`: Version evolution / roadmap. The problem statement comes from a release note, roadmap, or a multi-goal version requirement, and needs to satisfy multiple capability points and constraints at once.

Decision flow:
1. First read the task description and judge whether the user is asking to fix a bug, adjust behavior, add a capability, refactor/migrate, or perform version-level evolution.
2. Then look at whether the requirement is expressed concretely enough to directly point out the error/function, or only gives a behavior goal, compatibility requirement, version goal, or roadmap constraint.
3. If the task contains multiple levels at once, **list all of the levels that truly hold** (for example, if it both adds a capability and corrects an old behavior, output both `feature_addition` and `behavior_adjustment`).
4. If a task is essentially about adding a capability, even if it also incidentally modifies an old path or adds tests, it should at least include `feature_addition`.
5. If a task is essentially an internal replacement or migration and explicitly requires external behavior to remain unchanged, it should at least include `refactor_or_migration`.
6. If the task clearly comes from a release note, version-upgrade goal, or roadmap planning, and there are multiple goals or version-level constraints, it should at least include `release_or_roadmap`.

Some distinguishing hints:
- Directly saying "a certain function errors out / a certain test failed / a certain input crashes" is closer to `explicit_bug`.
- Saying "this API should support some kind of edge case / the semantics should be adjusted to ..." is closer to `behavior_adjustment`.
- Saying "add a certain capability / support a certain new entry point / add a certain new mode" is closer to `feature_addition`.
- Saying "replace an internal mechanism / migrate an implementation / tidy up structure, but external behavior is unchanged" is closer to `refactor_or_migration`.
- Saying "implement the next version's capability points / align with the release note / satisfy multiple goals on the roadmap" is closer to `release_or_roadmap`.

Quality checks:
1. Output a **list of labels**, with at least 1 label; only give multiple when they truly hold, and do not force in unrelated levels.
2. Each label must come from the fixed set:
   - `explicit_bug`
   - `behavior_adjustment`
   - `feature_addition`
   - `refactor_or_migration`
   - `release_or_roadmap`
3. `reason` must concisely explain why these levels, rather than the adjacent levels.
4. If the information is insufficient, still choose the most reasonable one based on the available evidence; do not return an empty list or invent labels.

Output JSON only:

  "requirement_depth": ["feature_addition"],
  "reason": "one sentence explaining why this task belongs to these levels"
