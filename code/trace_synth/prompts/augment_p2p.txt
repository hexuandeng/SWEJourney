Core constraint: fresh perspective, no duplication
================================================================
`all_declared_own` lists all test nodes declared by all events in the entire trace history. `current_own_f2p` and `current_own_p2p` are the test nodes already present in the current event itself. The test code for these nodes will be automatically applied and take effect in the docker baseline, meaning the angles they cover **have already been handled**.

Your task is to design **entirely new** regression protection tests:
- Cut in from angles not yet covered, for example: different input combinations, boundary conditions, error paths, caller perspectives, behavioral contracts of adjacent modules, parameterized variants, or code branches touched by `patch` but not yet covered by existing tests.
- Strictly forbidden to output any test identifier that has already appeared in `all_declared_own` (exact match, including parameterized suffixes).
- Even if you think a certain existing test "could also serve as a P2P", do not re-declare it — it has already been covered, duplication is meaningless.
- Function names defined in new `test_patch` must also not share names with any functions already in `all_declared_own`.

Available tools: docker_cli / reset_worktree
================================================================
If the fields in the input are insufficient to determine file content, diff context, runnable test locations, test identifiers, or the current accumulated code state, you may request the host to execute docker_cli commands via native tool_calls before outputting the final AUGMENT_TESTS JSON, or use reset_worktree to restore the worktree.

The working directory of docker_cli is the repo cwd configured in the container (typically /testbed for Verified, /app for Pro). The host will first construct the starting worktree, so the code state you see when entering docker is the baseline "**before applying the current ATTEMPT's model patch (`patch` field)**" — i.e., base_commit + historical successfully-applied ATTEMPT model patches (excluding the current ATTEMPT) + the complete `test_patch` of the current ATTEMPT (i.e., the full content of `current_test_patch`). In other words, the test file changes newly added by the current attempt are already in effect in the worktree, but the product code changes of the current attempt (`patch`) have not yet been applied.

This is perfectly consistent with the definition of P2P: P2P tests must PASS **before the patch** (i.e., in the current docker baseline), and still PASS **after the patch** (i.e., after additionally applying all changes in the current ATTEMPT's `patch` field). Therefore you can directly run candidate tests on this baseline worktree to verify "pass before patch"; to verify "still passes after patch", you need to first manually apply the current ATTEMPT's `patch` in docker_cli, then run the same set of tests. reset_worktree can restore the baseline (pre-patch state) at any time.

Multiple docker_cli calls share the same container and worktree, **state accumulates between calls** (e.g., files remain modified after git apply). After the final AUGMENT_TESTS JSON output, the host will close the container uniformly.

⚠️ **test_patch must be applicable on the baseline worktree**: Before submitting the final AUGMENT_TESTS JSON, you must first use reset_worktree to restore the baseline, then verify via docker_cli that `git apply --check` can successfully apply your test_patch in the baseline state, then output the JSON after confirmation.

Only docker_cli and reset_worktree are available; do not request other tools. Maximum 60 tool call invocations total. After receiving an observation, continue with tool_calls or output the final AUGMENT_TESTS JSON; the final JSON must still satisfy the output schema below, and must not contain tool / command / observation fields.

Patch generation method (mandatory; applies to `test_patch`)
================================================================
⚠️ This is the #1 cause of TEST_PATCH_APPLY_FAIL / `corrupt patch at line N` / `patch does not apply`. Follow it exactly.
- It is forbidden to hand-write or hand-edit the `@@ -start,len +start,len @@` hunk headers. Manually counting hunk line numbers is unreliable and is the direct cause of `corrupt patch` and `patch does not apply`. Even if you can recite the line-count rule, you will still miscount; do not try.
- The only allowed way to produce a diff is: (1) reset_worktree to restore the baseline; (2) use docker_cli to directly edit the target file(s) in place (e.g., write the whole file with python/cat, or use sed); (3) export the diff with `git diff -- <file>` (for brand-new files, run `git add -N <file>` first so `git diff` includes them); (4) take that exported diff string verbatim, byte-for-byte, as the element of `test_patch`. Do not hand-modify a single character of the exported diff afterwards.
- The test_patch you write into the final JSON MUST be the exact same byte-for-byte string that you just exported via `git diff` and confirmed with `git apply --check` in docker. Verifying one string in docker and then submitting a re-typed, "cleaned-up", or re-indented version is the most common failure mode: the verified object and the submitted object must be identical.
- Final gate before submitting: reset_worktree, then write the exact test_patch string that is going into the JSON into a file and run `git apply --check` on it; only submit after it passes.
