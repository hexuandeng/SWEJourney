Patch generation method (mandatory; applies to both `patch` and `test_patch`)
================================================================
⚠️ This is the #1 cause of TEST_PATCH_APPLY_FAIL / `corrupt patch at line N` / `patch does not apply`. Follow it exactly.
- It is forbidden to hand-write or hand-edit the `@@ -start,len +start,len @@` hunk headers. Manually counting hunk line numbers is unreliable and is the direct cause of `corrupt patch` and `patch does not apply`. Even if you can recite the line-count rule, you will still miscount; do not try.
- The only allowed way to produce a diff is: (1) reset_worktree to restore the baseline; (2) use docker_cli to directly edit the target file(s) in place (e.g., write the whole file with python/cat, or use sed); (3) export the diff with `git diff -- <file>` (for brand-new files, run `git add -N <file>` first so `git diff` includes them); (4) take that exported diff string verbatim, byte-for-byte, as the element of `patch` / `test_patch`. Do not hand-modify a single character of the exported diff afterwards.
- The patch you write into the final JSON MUST be the exact same byte-for-byte string that you just exported via `git diff` and confirmed with `git apply --check` in docker. Verifying one string in docker and then submitting a re-typed, "cleaned-up", or re-indented version is the most common failure mode: the verified object and the submitted object must be identical.
