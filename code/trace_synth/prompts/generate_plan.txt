The four BigTask-level dim_tags definitions are as follows:

1. context_scope (str, single label): what context is needed at minimum to understand and complete this BigTask. Possible values:
   - `no_context`: no code, files, or logs needed; can be completed with natural language alone.
   - `snippet`: only the problem, code snippet, error, or diff snippet given by the user/SEED/history is needed.
   - `single_file`: need to understand the definitions, imports, class/function relationships, or file-level control flow within a complete file.
   - `multi_file`: need to understand the collaborative relationship between multiple files or multiple files within the same module/package.
   - `repo`: need to understand the entire repository structure, project conventions, dependency management, build methods, or test system.

2. change_scope (str, single label): how large an engineering scope the final code, configuration, scripts, or documentation changes affect. Possible values:
   - `no_change`: no artifact modification, only explanation, analysis, or advice.
   - `local`: a single local point or logical unit, e.g., one function, method, class, component, or configuration block.
   - `single_file`: modification of multiple logical units within a single file, or file-level structural adjustment.
   - `multi_file`: multiple files, changes within the same module/package/component, without changing cross-component contracts.
   - `cross_component`: cross-component collaborative logic, or changes to public API / CLI / schema / protocol.

3. requirement_depth (str, single label): what level the requirement abstraction and task type of this BigTask is at. Single label. Possible values:
   - `refactor_or_migration`: pure internal refactoring or migration. The problem only requires tidying internal structure, renaming, or relocating implementations, with minimal change scope and no change to external behavior. This is the simplest tier.
   - `explicit_bug`: explicit bug. The problem directly points out a function, error symptom, error report, or a very narrow fix target.
   - `behavior_adjustment`: behavior adjustment. The problem requires a certain behavior to support a certain boundary case or correct semantics, but does not directly give file names.
   - `feature_addition`: feature addition. The problem requires adding a certain capability, while usually also maintaining old behavior or compatibility paths.
   - `release_or_roadmap`: version evolution / roadmap. The problem comes from release notes, roadmap, or multi-target version requirements, needing to satisfy multiple capability points and constraints simultaneously.

4. knowledge_domains (list[str], multi-label): what technical knowledge domains completing this BigTask requires. These are open labels, but must be summarized from history / SEED / patch / test / error evidence, do not fabricate. Naming requirements: use abstract knowledge domain or stable technical subdomain names; do not use task intent category names (e.g., fix/extend), and do not use requirement depth label names (e.g., R1/R2/R3, etc.). Can be summarized from the following evidence: repo/package/module names, file paths, imports, dependencies, frameworks, tools, protocols, issue terminology, APIs/data structures/test assertions/configuration mechanisms involved in the patch, traceback/logs.

5. new_task_angle (list[str], multi-label): the 1 or more "task angle" labels you selected in Step 3 as the main attack direction of this BigTask. Copy the chosen label name(s) **verbatim** from the candidate list in {{ANGLE_CANDIDATES}} (the label name before the colon only, without the definition text). Must be a non-empty subset of the candidates provided this round; do not invent new angle names and do not include candidates you did not select.

Dimension breakthrough rules:
- Among the four dimensions, context_scope / change_scope / requirement_depth are single-label dimensions; "stronger" means selecting a label further in the ordering: context_scope: no_context < snippet < single_file < multi_file < repo; change_scope: no_change < local < single_file < multi_file < cross_component; requirement_depth: refactor_or_migration < explicit_bug < behavior_adjustment < feature_addition < release_or_roadmap.
