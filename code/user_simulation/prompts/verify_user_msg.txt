What you are judging: the interaction realism of this one candidate user message
================================================================
Score candidate_message on the seven dimensions below. Each dimension is an independent integer score from 1 to 5; a low score means the message is unrealistic on that dimension and should be regenerated. Combine the rendered persona, real subtask_status, and complete transcript, and judge the message as actually written. First settle the current persona in your mind, then judge whether this user behaves realistically under that persona; do not score mechanically by behavior counts and do not invent facts not present in the input.

1) user_language_naturalness -- user language naturalness
Whether the single utterance itself sounds like a real user speaking during collaboration, and fits the current persona (a non_programming_user may be colloquially confused, a product_stakeholder leans business, a repo_newcomer_engineer has engineering judgement, a repository_steward is professional and concise). Only judge whether tone and wording are natural, whether there is real-user elision/colloquialism/emotion/professional expression, and whether it avoids template-like, overly tidy task-spec phrasing. Do not judge answer leakage, information timing, or context continuation here.
  1 Clearly template-like, like a one-shot benchmark spec; overly tidy and complete, with almost no trace of a real user.
  2 Mostly still template-like, with natural traces only in a few spots; weak match to the persona's language style, or persona mismatch exists.
  3 Some natural expression, but overall still leans toward a task spec; some sentences sound human and some sound like a benchmark, with minor persona mismatch.
  4 Most expression is natural and basically fits the persona; occasional minor template-ness or over-tidiness.
  5 Highly natural and clearly fits the persona; tone, wording, elision, and professional level all read like a real user in collaboration.

2) non_oracle_input -- non-oracle input (including test-layer leakage)
Whether the user provides only information a real user could know in this scenario (goal, symptoms, business constraints, visible errors, results they ran themselves, reasonable maintainer constraints), without giving the agent the answer in advance like an oracle. It must never leak the hidden implementation path, concrete fix, private helper/function names, internal assertion conditions, exact diff, or requirements back-derived from the standard answer. This dimension also judges test-layer leakage: a real user does not know the evaluation machinery, so the message must never contain or imply "test / hidden test / test case", "subtask", "checklist", "rubric / scoring", "FAIL_TO_PASS / PASS_TO_PASS / f2p / p2p", "S1 / S2 subtask ids", "benchmark / SWE-bench / reference patch / gold patch / test patch", and must not say a test passed/failed or name any test case/file. Any solution step, anything close to the gold diff, or any test/evaluation-layer wording scores 1. This dimension also checks test-patch content leakage: the agent cannot see the test patch or final hidden test files, so any symbol that exists only in the test patch (private method/variable/field name assumed by a test, assertion condition, test function name, line number, testdata literal, etc.) is content the agent cannot learn. If the candidate message pastes verbatim OR paraphrases a machine error from `run_subtask_test` containing such test-patch-only symbols, score 1; a real user should paraphrase it as a natural-language symptom/expectation. **[HARD RULE, independent of whether it was quoted verbatim] If the message contains ANY test filename of the form `*_test.go` / `*_test.py` / `*_test.*` / `*Test.java`, ANY `filename:linenumber` location reference, or ANY `TestXxx` / `test_xxx` test function name -- whether pasted verbatim or already rewritten into fluent natural language (e.g. "the test file db_test.go is calling Open with too many args" / "the test invokes function X"), this dimension scores <= 2.** The criterion is the OBJECTIVE presence of a test filename / line number / test function name, NOT whether the machine error was quoted word-for-word -- rewording a machine error into a smooth sentence does NOT grant an exemption. A real user cannot see the test files and can only phrase things as a business/product-level symptom (e.g. "right after I change the flag and read it back I still get the old value" / "the build won't pass"); they would never name any test file or test function. Exception (cross-persona required-name relay): if the agent's implementation direction is correct and it only lacks one necessary name/label/interface shape that can only be known from the hidden tests and cannot be inferred on its own (a specific variable/method/field/function name a test assumes, or the exact interface shape), then the user stating that one concrete name is NOT leakage and must NOT be scored down here. This holds for EVERY persona and even if the user never ran any test/verification: a technical persona may phrase it as a naming/interface convention ("I want this called XX" / "let's agree the interface looks like this"); a non-technical persona (non_programming_user / product_stakeholder) may relay it as plain surface text they were handed ("the spec says it must be called XX" / "I was told the label has to be exactly XX"). Do not penalize a non-technical persona for producing this one code-adjacent string — the carve-out overrides the "private helper/function names" and "test-patch-only symbol" bans for this single necessary name. The exception is valid ONLY when: the agent's direction is right and it is purely blocked on that name; the name is a **product-side interface name** (a variable/method/field/function name in the product/code under test), **NOT** a test filename, a test function name, or a private symbol assumed by a test; the message reveals no other implementation step, no gold-diff-like content, and no test-layer vocabulary, raw or paraphrased machine error, line number, or assertion condition. **[EXEMPTION EXCLUSION] The moment the message also contains ANY `*_test.*` test filename, any `filename:linenumber` reference, any `TestXxx` / `test_xxx` test function name, or ANY paraphrase of a compile/test error, this exemption is immediately void and falls back to the `<= 2` ruling above; the carve-out covers only a SINGLE product-side interface name, and never covers a "set of test-expected signatures/files/symbols".** If the user hands over a name while the agent's direction is wrong, or bundles it with extra fix steps or any test-layer wording, that is still leakage and scores low.
[NEVER ASK THE AGENT TO MODIFY TESTS] Hidden tests are the acceptance ground truth; the agent cannot see or modify them. The only legitimate path is to change the product/code under test so behavior matches expectations, not to touch tests. The candidate must never ask, hint, or steer the agent toward changing tests, editing cases, adjusting assertions, loosening checks, skipping checks, commenting out validation, or making a failing check pass. Any wording that has the agent modify, weaken, or bypass tests/validation itself scores 1, and `issues` should say to rewrite toward "make the code match the expectation" rather than "make tests bend to code".

  3 Locally oracle-ish: gives an overly detailed implementation direction or internal detail, but the body is still goal/symptom/constraint.
  4 Basically no leakage; only a little borderline technical hint, still explainable as something a real user might know.
